# TfL Meeting Point

A full-stack analytical tool that models the London Underground, Overground, and Elizabeth Line as a weighted graph to calculate the optimal meeting point between 2–6 people — live disruption aware, and built on real TfL data.

## Overview

Most "find a meeting point" tools naively calculate a geographic midpoint. This project does something more interesting: it models the entire TfL network as a weighted directed graph and applies **Dijkstra's algorithm** — O(E + V log V) — to find the station that minimises the maximum travel time across all participants. This "fairness metric" ensures no one person travels significantly more than another.

Live disruption data from the TfL Unified API is factored into edge weights in real time, so if the Piccadilly line has severe delays, those segments become proportionally more expensive for the algorithm to route through.

---

## Features

- **Optimal meeting point** for 2–6 people simultaneously
- **Dijkstra's algorithm** with a custom binary min-heap implementation
- **Live disruption awareness** — TfL line status inflates edge weights in real time, with expandable disruption details
- **Journey breakdown** per person — line-by-line with interchange points, direction, and travel times per segment
- **Interactive route map** powered by Leaflet.js on a CartoDB dark tile layer
- **Shareable links** — results encoded as URL parameters for easy sharing
- **Auto-restore** — shared links recalculate the result on load
- **Full network coverage** — Tube (11 lines), Elizabeth Line, and all 6 named Overground lines (Lioness, Mildmay, Weaver, Suffragette, Windrush, Liberty)

## Architecture

### The Graph Model

Every TfL station is a **node** and every rail segment is a **weighted directed edge**, where the weight is the travel time in minutes. Interchange walks between platforms at the same station (e.g. Paddington National Rail → Paddington Elizabeth Line) are modelled as additional edges with a configurable walk-time penalty.

```
G = (V, E)

V = { all TfL stations (NaPTAN IDs) }
E = { (from, to, line, travelTime) }
  + { (a, b, "interchange", walkTime) for same-name stations with different NaPTAN IDs }
```

### Travel Time Sources

Tube segment times are sourced from a Freedom of Information request dataset (FOI-derived, via nicola/tubemaps), matched to TfL's NaPTAN station IDs by name. Elizabeth Line and Overground segment times use a Haversine approximation at average TfL inter-peak speeds (~33 km/h). The dataset is generated once by a build script and committed to the repo.

### The Meeting Point Algorithm

For N people, the algorithm:

1. Runs Dijkstra's from each person's origin station simultaneously
2. For every candidate station, computes `max(t₁, t₂, ..., tₙ)` — the "fairness metric"
3. Selects the candidate that minimises that maximum, breaking ties by minimising total combined travel time

### Live Disruptions

The TfL `/Line/Mode/{modes}/Status` endpoint is polled every 60 seconds. Each line's **worst** status (lowest severity code) is used to derive a multiplier applied to that line's edge weights before Dijkstra runs:

| Severity | Status | Multiplier |
| :--- | :--- | :--- |
| 0 | Suspended | ∞ (impassable) |
| 1 | Closed | 10× |
| 5 | Part Suspended | 3× |
| 6 | Severe Delays | 2× |
| 9 | Minor Delays | 1.5× |
| 10 | Good Service | 1× |

## Getting Started

### Prerequisites

- Node.js 18+
- A TfL API key (free — register at [api.tfl.gov.uk](https://api.tfl.gov.uk))

### Installation

```bash
git clone https://github.com/Jacob-Dawson/tfl-helper.git
cd tfl-helper
npm install
```

### Environment Setup

Create `client/.env`:

```
VITE_TFL_API_KEY=your_key_here
```

Create `.env` at the root (for the build script):

```
TFL_API_KEY=your_key_here
```

### Generate the Dataset

This is a one-time step that fetches station and route data from the TfL API and builds the static graph files:

```bash
npx ts-node --project tsconfig.json scripts/buildDataset.ts
```

This will output `client/src/data/stations.json` and `client/src/data/connections.json`. The script logs a summary showing how many segments used FOI-derived times vs Haversine approximations.

### Run the App

```bash
npm run dev
```

The app will be available at `http://localhost:5173`.

## Limitations

- **National Rail** stations outside TfL-operated services are not included (e.g. Hornsey, Crayford, Sutton). The network covers Tube, Elizabeth Line, and Overground only.
- **Overground travel times** are Haversine approximations rather than timetable-derived values.
- **Interchange times** use a flat 3-minute default with manual overrides for major stations. Actual walk times vary.
- The dataset is **static** — re-run the build script periodically to capture new stations or line changes.

## Recruiter Notes

This project was built to demonstrate:

- **Graph theory in practice** — a from-scratch Dijkstra implementation with a binary min-heap, not a library call
- **Real-world API integration** — handling TfL's data model, NaPTAN ID system, and multi-status line responses
- **System design thinking** — the pipeline architecture (static graph + live disruption overlay) separates concerns cleanly
- **Frontend engineering** — React context, custom hooks, D3-style coordinate projection, Leaflet map integration
- **Data sourcing** — cross-referencing an FOI dataset with a live API to build a reproducible, documented graph
